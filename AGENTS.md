1. Название проекта и описание

**Ассистент для редактора** — одностраничное веб‑приложение, которое помогает редакторам (и смежным ролям) проверить клиентский бриф/запрос на полноту, найти пробелы и противоречия, собрать вопросы и черновик «понимания задачи».

2. Tech Stack

- **Frontend**: один статический файл `Assistant.html` (HTML + CSS + Vanilla JS).
- **Хранение состояния**: `localStorage` (ключ `editorassistant.v1`).
- **Хостинг/деплой**: Netlify (настройка в `netlify.toml`, публикация из корня репозитория).
- **Шрифты**: Google Fonts (`Inter`).
- **AI-режим**: Netlify Function `netlify/functions/analyze-brief.js` обращается к OpenAI Responses API через `OPENAI_API_KEY`.
- **Вспомогательный скрипт (CLI)**: `ask_ai.py` (Python) + `python-dotenv` + `openai` SDK (для обращения к OpenAI API).

3. Project Structure

- **`Assistant.html`**: всё приложение в одном файле (верстка, стили, логика анализа).
  - Внутри: экран ввода → экран разбора → экран добавления ответов клиента.
  - Правила анализа: массивы `CATEGORIES` и `CONTRADICTION_RULES`.
- **`README.md`**: как открыть локально и как публиковать на Netlify.
- **`PRODUCT_SCENARIOS.md`**: поведенческие сценарии текущего MVP; источник правды для реализации продуктового поведения.
- **`netlify.toml`**: конфиг статической публикации и редирект `/` → `/Assistant.html`.
- **`netlify/functions/analyze-brief.js`**: serverless-функция для AI-разбора брифа; ключ OpenAI остаётся на серверной стороне.
- **`spec.md`**: PRD/требования (в т.ч. будущий план развития).
- **`ask_ai.py`**: утилита для тестового запроса к OpenAI (генерация названий по описанию из README).
- **`.env`**: локальные переменные окружения для `ask_ai.py` и Netlify Dev (не коммитится).
- **`.gitignore`**: исключения (сейчас содержит `.env`).

4. Conventions

- **Коммиты**: **Conventional Commits** — `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`, `style:`, `test:`.
- **Синхронизация правил**: `AGENTS.md` и `.cursorrules` должны обновляться вместе. Если меняешь один файл, внеси эквивалентное изменение во второй в той же правке.
- **Ветки**:
  - **`main`**: production (мерж в `main` триггерит Netlify deploy).
  - **Рабочие ветки**: `feat/<short-description>`, `fix/<short-description>`, `docs/<short-description>`, `chore/<short-description>` (только `kebab-case`).
- **Именование файлов**:
  - Статическое приложение держим **single-file**: изменения по UI/логике в первую очередь делаем в `Assistant.html`.
  - Новые файлы добавляй только когда это оправдано инфраструктурой или изоляцией секрета/интеграции: например, Netlify Functions, документация, CLI-утилиты.
  - UI/CSS/клиентскую логику не дробим без отдельного решения владельца проекта; по умолчанию сохраняем монолит `Assistant.html`.
  - Если появятся новые файлы, называем их **латиницей**, `kebab-case`, по назначению (пример: `rules-ru.json`, `app.css`, `analysis.js`).
  - Исключение: верхнеуровневые документы-источники правды могут быть в `UPPER_SNAKE.md` по явному решению владельца проекта (например, `PRODUCT_SCENARIOS.md`, `AGENTS.md`, `README.md`).

5. Environment

Переменные окружения (без значений):

- **`OPENAI_API_KEY`**: нужен для `ask_ai.py` и для `netlify/functions/analyze-brief.js` при локальном `netlify dev` / в Netlify Environment variables.
- Других обязательных переменных окружения сейчас нет.

## Визуальный спек — ASCII-схемы

### В документации
При создании или обновлении любого .md-файла добавляй ASCII-схемы в разделах, где визуал помогает схватить суть быстрее текста:
- Архитектура → блоки сервисов и стрелки с подписями протоколов
- Структура проекта → дерево папок с пояснениями
- User flow → экраны и переходы со стрелками
- UI-макет → блоки страницы с подписями и примерами данных
- Связи компонентов → блоки и стрелки импортов

Схемы — в ``` блок, текст раздела не переписывай, только дополняй.

### Перед новым функционалом (до кода)
Если задача — добавить новый экран, модуль или интеграцию: сначала нарисуй ASCII-схему (UI-вайрфрейм, архитектура, user flow или связи компонентов). Покажи мне, дождись подтверждения и только потом пиши код.

6. What Claude Should Know

- **Офлайн/fallback‑принцип**: приложение должно оставаться полезным локально в браузере без настроенного бэкенда: если Netlify Function или OpenAI недоступны, включаются эвристики/правила. AI‑режим разрешён только через `netlify/functions/analyze-brief.js`, без передачи ключа во фронтенд.
- **Ядро логики**: категории и критерии “зелёный/жёлтый/красный” живут в `CATEGORIES`; противоречия — в `CONTRADICTION_RULES`. Любые изменения в продуктовой логике делай через эти структуры, а не через разбросанные if’ы.
- **Сценарий использования**: пользователь вставляет сырой текст (письмо/чат/расшифровка), получает:
  - разбор по блокам (контекст/проблема/задача/решение/конечный результат/сроки),
  - список вопросов,
  - черновик «понимания задачи» (копируемый текст),
  - подсветку противоречий.
- **Состояние**: приложение восстанавливается из `localStorage` и “продолжает” со 2/3 экрана, если уже был разбор.
- **Границы проекта**:
  - `ask_ai.py` — вспомогательная утилита и не влияет на работу `Assistant.html`.
  - `netlify/functions/analyze-brief.js` — единственная серверная часть основного сценария; она нужна для AI‑режима, но приложение должно иметь локальный fallback.
  - `spec.md` содержит требования/видение, но текущая реализация — статический MVP с optional AI‑режимом.
- **Шаг 0 перед изменениями**: сначала зафиксируй целевой результат в 1–2 фразах (что должно получиться на экране/в поведении), и только потом вноси кодовые правки. Это снижает риск “поплывшего” ТЗ.
- **Пустоты в требованиях**: если данных не хватает, сделай не более 2 явных допущений (помечай как допущения); если без этого нельзя безопасно двигаться — остановись и попроси одно конкретное уточнение.
- **Пояснение изменений простым языком**: после правок кратко объясняй, что изменилось и зачем, без жаргона и без очевидных технических деталей; фокус на эффекте для редакторского процесса.
- **Бизнес‑правила/тон**: хороший бриф даёт контекст, проблему, задачу, ожидаемый результат, ограничения/решение и сроки. Перед стартом критичны задача, результат и сроки; вопросы `must` — только блокеры старта, `should` — полезные уточнения. Тон подсказок: дружелюбный, прямой, без обвинений клиента.

7. Don't

- **Не начинай правки без зафиксированного результата** (что именно должно измениться в поведении приложения).
- **Не добавляй сервер/сборку/фреймворк** (Next.js, Vite, React и т.п.), если задача решается в `Assistant.html`.
- **Не отправляй текст пользователя во внешние API напрямую из браузера** и не включай аналитику/трекинг без явного решения владельца проекта. Для AI‑анализа используй только согласованный путь через Netlify Function и серверный `OPENAI_API_KEY`.
- **Не коммить секреты** (`.env`, ключи API, токены) и не оставляй их в истории изменений.
- **Не ломай рабочий сценарий и инфраструктуру MVP**: поток экранов (ввод → разбор → дополнение) и редирект Netlify `/` → `/Assistant.html` должны оставаться валидными.


## Dogfooding: self-check before "готово"

После любой UI-правки или правки логики, влияющей на интерфейс, ты (агент) обязан:

1. Сделать правку в коде.
2. Открыть URL приложения через Playwright MCP. URL — опубликованный (Lovable / Vercel / Netlify / GitHub Pages / прод) или локальный `http://localhost:PORT` от `npm run dev`, указан в README или в моём сообщении. Если Playwright MCP не подключён — остановись и попроси меня подключить, не пытайся симулировать проверку из кода.
3. Найти изменённый элемент и **прокликать связанный сценарий**: кнопку — нажать; форму — заполнить и отправить; переход — пройти; вкладку/раскрывашку/окошко — переключить. Сделать скриншоты до и после взаимодействия.
4. Посмотреть на скриншоты: правка реально применилась? клик/submit/переход сработал? не сломал ли соседнее? адаптив не съехал?
5. Если внешний вид или поведение сломаны — поправить и повторить. После двух итераций без прогресса — остановись и расскажи о тупике.
6. Сообщать "готово" только после подтверждения и внешнего вида, и поведения. Скриншоты прикладывай к финальному сообщению.
