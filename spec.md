## PRD

**Название проекта:**  
Ассистент редактора

**Описание (2–3 предложения):**  
Веб-приложение, которое помогает разобрать клиентский запрос до старта черновика. Пользователь загружает вводные по задаче, получает разбор пробелов, противоречий и рисков, список точных вопросов клиенту и затем собирает согласуемое «понимание задачи». Продукт решает проблему позднего обнаружения неясностей, когда поломка запроса вскрывается уже на этапе текста и переделок.

**Целевая аудитория:**  
Редакторы и смежные роли, работающие с клиентскими контентными задачами: штатные редакторы, редакторы в агентствах, фрилансеры, аккаунт-менеджеры, авторы.

**Ключевая проблема:**  
Сейчас клиентский запрос часто выглядит понятным только на словах. Реальные пробелы, противоречия и недостающие вводные обнаруживаются уже после начала работы над черновиком, из-за чего растут переделки, появляются новые вводные задним числом и ломается процесс согласования.

**Устройства:**  
Веб: браузер на ноутбуке и телефоне.

**Бюджет на хостинг:**  
До 5 долларов в месяц.

**Дедлайн MVP:**  
Не фиксируется. Приоритет — качественная рабочая версия, а не выпуск к конкретной дате.

## Requirements

### MVP (обязательно для первой версии)
- [Создание карточки задачи]
- [Ввод клиентского запроса в текстовом виде]
- [Хранение всех вводных внутри одной карточки задачи]
- [Разбор запроса по ключевым блокам: контекст, проблема, задача, результат, ограничения, сроки]
- [Выявление пробелов в запросе]
- [Выявление типовых противоречий в запросе]
- [Пояснение, почему каждый пробел или противоречие мешает старту работы]
- [Формирование уточняющих вопросов к клиенту]
- [Разделение вопросов по критичности: обязательно до старта / желательно уточнить]
- [Внесение ответов клиента в карточку задачи]
- [Повторный прогон карточки после обновления вводных]
- [Сборка черновика “понимания задачи” для согласования с клиентом]
- [Копирование вопросов клиенту]
- [Копирование текста “понимания задачи”]
- [Статус карточки: есть критичные пробелы / можно согласовывать]

```text

+----------------------------------------------------------------+
```

## Tech Stack

| Компонент | Технология | Почему для моего проекта | Бесплатно? | ИИ пишет на этом хорошо? |
|---|---|---|---|---|
| Фронтенд | **Один статический файл `Assistant.html` (HTML + CSS + Vanilla JS)** | Текущий MVP держит интерфейс, стили и клиентскую логику в одном файле без сборки. Это снижает сложность поддержки и позволяет открыть приложение локально прямо в браузере. | Да | **Да.** Изменения легко делать точечно внутри одного файла. |
| Локальное состояние | **`localStorage` (`editorassistant.v1`)** | Нужно восстановить введённый бриф, ответы клиента и текущий экран без аккаунтов и базы данных. | Да | **Да.** Простая браузерная API без инфраструктуры. |
| Локальный анализ | **Эвристики в `CATEGORIES` и `CONTRADICTION_RULES`** | Приложение остаётся полезным без настроенного AI: категории, пробелы и типовые противоречия считаются на клиенте. | Да | **Да.** Правила можно расширять без изменения архитектуры. |

| Хостинг | **Netlify** | Репозиторий публикуется из корня, `netlify.toml` задаёт `publish = "."` и редирект `/` → `/Assistant.html`. | Да, для MVP | **Да.** Конфигурация минимальная. |
| Вспомогательный CLI | **`ask_ai.py` + `python-dotenv` + `openai` SDK** | Утилита для тестовых запросов к OpenAI отдельно от основного веб-сценария. | OpenAI API usage-based | **Да.** Не влияет на работу приложения. |

## Data

Текущий MVP хранит состояние в `localStorage` по ключу `editorassistant.v1`. Модель ниже описывает целевую структуру данных на случай появления базы данных, авторизации и истории личных карточек: данные карточек принадлежат одному пользователю, не разделяются между клиентами или командами, удаление карточки работает как архивирование, а история изменений и аудит не ведутся.

### `users`

Личный аккаунт редактора. В MVP может отсутствовать как отдельная таблица, но нужен для будущей авторизации и изоляции данных.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор пользователя. |
| `email` | `text` | Да | — | Email для входа. |
| `name` | `text` | Нет | — | Отображаемое имя пользователя. |
| `created_at` | `datetime` | Да | — | Когда пользователь создан. |
| `updated_at` | `datetime` | Да | — | Когда профиль обновлён. |

### `task_cards`

Карточка редакторской задачи: хранит исходный клиентский запрос, текущий статус и состояние архивирования.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор карточки. |
| `user_id` | `uuid` | Да | `users.id` | Владелец карточки. |
| `title` | `text` | Нет | — | Короткое название задачи, может генерироваться из запроса. |
| `client_request` | `text` | Да | — | Сырой текст письма, чата, расшифровки или другого брифа. |
| `status` | `enum` | Да | — | `has_critical_gaps` или `ready_for_approval`. |
| `screen_state` | `enum` | Да | — | Текущий экран: `input`, `analysis`, `client_answers`. |
| `archived_at` | `datetime` | Нет | — | Заполнено, если карточка архивирована вместо удаления. |
| `created_at` | `datetime` | Да | — | Когда карточка создана. |
| `updated_at` | `datetime` | Да | — | Когда карточка или её актуальное состояние изменены. |

### `analysis_results`

Последний актуальный разбор карточки. Повторный прогон перезаписывает этот результат, отдельная история прогонов не хранится.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор разбора. |
| `task_card_id` | `uuid` | Да | `task_cards.id` | Карточка, к которой относится разбор. |
| `mode` | `enum` | Да | — | Источник разбора: `heuristic` или `ai`. |
| `summary` | `text` | Нет | — | Короткое резюме состояния брифа. |
| `contradictions_json` | `json` | Нет | — | Найденные противоречия с объяснениями и ссылкой на правило. |
| `critical_gap_count` | `integer` | Да | — | Количество блокеров старта. |
| `recommended_status` | `enum` | Да | — | Рекомендованный статус карточки после разбора. |
| `analyzed_at` | `datetime` | Да | — | Когда выполнен последний прогон. |
| `updated_at` | `datetime` | Да | — | Когда результат был обновлён. |

### `analysis_blocks`

Структурные блоки разбора: контекст, проблема, задача, результат, ограничения и сроки.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор блока. |
| `analysis_result_id` | `uuid` | Да | `analysis_results.id` | Разбор, внутри которого находится блок. |
| `block_type` | `enum` | Да | — | `context`, `problem`, `task`, `result`, `constraints`, `deadline`. |
| `status` | `enum` | Да | — | `green`, `yellow` или `red`. |
| `extracted_text` | `text` | Нет | — | Что удалось извлечь из брифа по этому блоку. |
| `gap_explanation` | `text` | Нет | — | Почему пробел мешает старту или согласованию. |
| `sort_order` | `integer` | Да | — | Порядок показа блока в интерфейсе. |

### `clarification_questions`

Уточняющие вопросы клиенту, сформированные по последнему разбору.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор вопроса. |
| `analysis_result_id` | `uuid` | Да | `analysis_results.id` | Разбор, который породил вопрос. |
| `analysis_block_id` | `uuid` | Нет | `analysis_blocks.id` | Блок разбора, с которым связан вопрос. |
| `criticality` | `enum` | Да | — | `must` для блокеров старта или `should` для полезных уточнений. |
| `question_text` | `text` | Да | — | Формулировка вопроса клиенту. |
| `reason` | `text` | Нет | — | Почему ответ нужен редактору. |
| `sort_order` | `integer` | Да | — | Порядок показа вопроса. |

### `client_answers`

Ответы клиента, привязанные к конкретным уточняющим вопросам.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор ответа. |
| `question_id` | `uuid` | Да | `clarification_questions.id` | Вопрос, на который дан ответ. |
| `answer_text` | `text` | Да | — | Текст ответа клиента. |
| `created_at` | `datetime` | Да | — | Когда ответ внесён в карточку. |
| `updated_at` | `datetime` | Да | — | Когда ответ отредактирован. |

### `understanding_drafts`

Актуальный черновик «понимания задачи» для согласования с клиентом.

| Поле | Тип | Обязательное | FK | Описание |
|---|---|---:|---|---|
| `id` | `uuid` | Да | — | Уникальный идентификатор черновика. |
| `task_card_id` | `uuid` | Да | `task_cards.id` | Карточка, для которой собран черновик. |
| `draft_text` | `text` | Да | — | Текст «понимания задачи», доступный для копирования. |
| `generated_from_analysis_id` | `uuid` | Нет | `analysis_results.id` | Разбор, на основе которого собран черновик. |
| `updated_at` | `datetime` | Да | — | Когда черновик пересобран или отредактирован. |

```text

  | owns

  |                 N
```

## Implementation Notes

- Текущая реализация — статический MVP с optional AI-режимом, а не Next.js/Supabase/Vercel-приложение.
- Основной пользовательский поток остаётся: ввод запроса → разбор → ответы клиента → повторный прогон → понимание задачи.
- Для будущих расширений (история карточек, авторизация, память заказчика, интеграции) можно отдельно пересмотреть стек, но текущий код не требует фреймворка или базы данных.
